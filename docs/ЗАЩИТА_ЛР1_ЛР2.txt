ЛР1. ПОДРОБНО ЧЕРЕЗ GITHUB DESKTOP
=================================

Это основной вариант инструкции ЛР1. Ниже сохранён вариант с Git-командами
как справочник; повторно выполнять его после действий в Desktop не нужно.
Сейчас инструкция описывает будущие действия, а не выполненный GitFlow.

А. КАКИЕ ОКНА НУЖНЫ И ЧТО ОЗНАЧАЮТ КНОПКИ
----------------------------------------
GitHub Desktop — ветки, просмотр изменений, коммиты, отправка и получение кода.
VS Code — изменение файлов, запуск тестов, просмотр сайта.
Сайт github.com — Issue, PR, review, слияние и публикация выпуска.

Current Repository — выбранный репозиторий.
Current Branch — текущая ветка; всегда проверять перед коммитом.
Changes — изменения файлов, которые ещё не вошли в коммит.
History — уже созданные коммиты и их содержимое.
Commit — сохранить выбранные изменения в локальную историю.
Publish branch — впервые отправить ветку на GitHub.
Push origin — отправить новые локальные коммиты.
Fetch origin — узнать, что изменилось на GitHub; не равно получить изменения.
Pull origin — получить новые коммиты текущей ветки на компьютер.
PR — предложение объединить ветки; push сам по себе не является PR/слиянием.

В. СНАЧАЛА РАЗОБРАТЬ ТЕКУЩИЕ ИЗМЕНЕНИЯ
--------------------------------------
На момент подготовки есть несохранённые в Git изменения. Это НЕ ошибка.
В Desktop открыть Changes, нажимать каждый файл и читать diff справа.
Красное — удалённые строки, зелёное — добавленные.
Не выбирать Discard Changes: команда удаляет незакоммиченные изменения.
Не включать в демонстрационный коммит посторонние файлы.

В VS Code у вкладок README/VERIFICATION могут быть несохранённые старые версии.
При предупреждении о более новом файле нажать Compare, сравнить обе стороны,
сохранить нужный итог. Не нажимать Overwrite без сравнения.

Текущие тесты, документация и настройки — отдельная подготовительная работа.
Их нужно принять отдельной задачей и PR, а не выдавать за маленькое изменение,
сделанное на защите. Перед обычным переключением веток Changes должен быть пуст.
Если Desktop предлагает перенос незакоммиченных изменений, не выбирать наугад.
Bring my changes to ... переносит работу в новую ветку;
Leave my changes on ... оставляет её на исходной ветке (через сохранение Desktop).
Нужно заранее знать, какой задаче принадлежат эти изменения.

Г. ПОДГОТОВИТЬ DEVELOP (ОДИН РАЗ)

3. Current Branch -> найти develop.
4. Если develop уже существует, выбрать её, Fetch origin -> Pull origin,
   если предложено. Повторно создавать не нужно.
5. Если develop нет: Current Branch -> New Branch.
6. Name: develop. Основа/Start from: main, не случайная feature-ветка.
7. Нажать Create Branch, затем Publish branch.
8. Проверить, что сверху Current Branch = develop.

Отдельной подготовительной задачей обновить CONTRIBUTING.md под GitFlow:
feature от develop, PR функции в develop, release в main и обратно в develop.
Само создание develop не меняет правила и не доказывает полный GitFlow.

К. REVIEW И СЛИЯНИЕ
------------------
Другой участник под своим GitHub-аккаунтом:
1. Открывает PR -> Files changed, читает изменения.
2. В своей копии проверяет ветку и выполняет make verify; проверяет интерфейс.
3. Нажимает Review changes -> Approve -> Submit review, если всё верно,
   либо Request changes с конкретными замечаниями.
Автор не выдаёт свою самопроверку за review другого участника.
Для приватного репозитория доступ выдаётся через Settings -> Collaborators
уполномоченным владельцем; не публиковать пароли для совместного доступа.

Если есть замечания: исправить в ТОЙ ЖЕ feature-ветке, проверить,
Commit -> Push origin. PR обновится автоматически; новый PR не нужен.
После одобрения выбрать Merge pull request -> Create a merge commit
(через стрелку рядом с кнопкой, если выбран другой способ) -> Confirm merge.
Если слияние заблокировано правилами или конфликтом, не обходить ограничение.
После слияния закрыть Issue со ссылкой на PR, если она не закрылась сама:
автозакрытие задач обычно связано со слиянием в default branch, а не develop.

Desktop: Current Branch -> develop -> Fetch origin -> Pull origin.
В History проверить появление принятого изменения. Выполнить make verify.

Publish branch вместо Push origin — нормальное первое опубликование ветки.

ЛР1. СПРАВОЧНИК GIT-КОМАНД (АЛЬТЕРНАТИВА DESKTOP)
=============================

0. ПРЕДВАРИТЕЛЬНАЯ ПОДГОТОВКА
----------------------------
На Mac:

cd "/Users/swelock/Desktop/учеба/3курс/DevOps/Project_DevOps"
git status --short
git branch -a
git tag -n
git ls-remote --tags origin

На момент составления инструкции в проекте есть незакоммиченные изменения;
develop и release-ветки ещё не созданы. Старый процесс нужно привести к GitFlow.
Не переключать ветки и не делать pull поверх несохранённой работы.
Не применять git reset --hard, force push или массовое git add .
Сначала согласовать состав текущих изменений и сохранить их отдельной работой.
Проверить Compare для несохранённых вкладок VS Code; не выбирать Overwrite вслепую.

Правила в CONTRIBUTING.md нужно обновить: feature создаётся от develop,
PR функции направляется в develop; выпуск проходит через release в main.
Старые Issue и PR не заменяют новый процесс: создать настоящую новую задачу.
Удалённое обсуждение нельзя воспроизвести выдуманным review.

Для GitFlow используется следующая схема:
Issue -> feature/* -> PR в develop -> release/* -> PR в main -> тег
                                              -> обратно в develop

main — выпущенные версии.
develop — изменения для следующего выпуска.
feature/* — работа над отдельной задачей.
release/* — подготовка и проверка выпуска.
hotfix/* — срочное исправление выпущенной версии; в этом сценарии не требуется.

После сохранения текущей работы и при чистом git status:

git switch main
git pull --ff-only origin main

Если develop ещё не существует ни локально, ни на origin:

git switch -c develop
git push -u origin develop

Если develop уже создана — не создавать повторно:

git switch develop
git pull --ff-only origin develop

4. RELEASE И ТЕГ
----------------
Ниже 0.2.1 — пример нового номера, не обязательное значение.
Проверить локальные и удалённые теги, выбрать свободную следующую версию.
Существующий v0.1.0 не удалять и не перемещать.

git tag -n
git ls-remote --tags origin
git switch -c release/0.2.1

На release-ветке обновить фактический номер версии в интерфейсе и документации.
Не добавлять новые большие функции на этапе выпуска.

make verify
git diff
git add campus/templates/index.html
git diff --cached
git commit -m "chore: prepare version 0.2.1"
git push -u origin release/0.2.1

Если менялись другие файлы версии, добавить их явно перед коммитом.
На GitHub: PR release/0.2.1 -> main, review, слияние через merge-коммит.
После слияния, в чистом рабочем дереве на Mac:

git switch main
git pull --ff-only origin main
make verify
git tag -a v0.2.1 -m "Release 0.2.1"
git push origin v0.2.1

На GitHub создать и проверить PR release/0.2.1 -> develop,
чтобы изменения подготовки выпуска попали обратно в разработку.
Если различий нет, проверить, что develop уже содержит итоговый код выпуска;
не создавать фиктивный коммит только для пустого PR.

git switch develop
git pull --ff-only origin develop
make verify

Выпущенный тег должен указывать на принятый коммит main, а не на случайный
коммит feature-ветки. Слияние не обходится локальной командой вместо review.

5. ПОКАЗАТЬ ПУТЬ ИЗМЕНЕНИЯ
-------------------------
Открыть на GitHub: Issue -> PR функции -> review -> PR выпуска -> тег.
На Mac:

git log --graph --oneline --decorate --all -30
git show --no-patch v0.2.1
git show --no-patch v0.1.0
git show --stat 1b28c21

Первые команды показывают новую цепочку и версии (номер заменить своим).
Последняя показывает старый коммит разрешения конфликта;
это отдельный исторический эпизод, не новое действие GitFlow.

Объяснение: задача фиксирует требование, ветка изолирует изменение,
PR и review проверяют его, release готовит выпуск, тег фиксирует версию.

6. ОБЪЯСНИТЬ ПРАВИЛА
--------------------
Открыть CONTRIBUTING.md после актуализации под GitFlow.
Назвать правила: задача, отдельная ветка, проверки, review другого участника,
нет секретов, нет force push общей ветки, выпущенные теги не перемещаются.

make test       — автоматические проверки поведения приложения.
make test-raw   — стандартный подробный вывод pytest.
make quality    — статический анализ и проверка форматирования.
make format     — форматирование (изменяет файлы, затем повторить проверки).
make verify     — полный набор локальных проверок.

Эти строки с пояснениями не копировать как shell-команды.
Выполняемая команда для итоговой проверки:

make verify

7. ПОКАЗАТЬ ИСКЛЮЧЕНИЕ СЕКРЕТОВ И ЛОКАЛЬНЫХ ФАЙЛОВ
-------------------------------------------------
На Mac, из корня проекта:

git check-ignore -v .env .env.local instance/campus.sqlite3 .venv/bin/python
git ls-files -- .env '.env.*' '*.sqlite*' '*.db' '.venv/*'
git status --short
git diff --cached

Ожидается: правила игнорирования локальных файлов; среди перечисленных
отслеживаемых файлов допустима .env.example без настоящих секретов.
Не должно быть рабочей .env, файла базы, окружения или приватного ключа.
.gitignore не защищает файл, который ранее уже попал в Git.
Если настоящий секрет опубликован, его необходимо отозвать/заменить.


ЛР2. ДВЕ LINUX-МАШИНЫ
=====================

0. ПРОВЕРИТЬ ИСХОДНОЕ СОСТОЯНИЕ
------------------------------
Обе VM должны быть включены. Сначала убедиться, на какой машине консоль:

hostname
ip -br address

На Campus DB:

systemctl is-enabled postgresql
systemctl is-active postgresql
pg_lsclusters

На Campus App:

systemctl is-enabled campus
systemctl is-active campus
curl -i --max-time 15 http://127.0.0.1:8000/health

Ожидается: enabled, active, кластер online, HTTP 200 и database/status ok.
Если исходное состояние неисправно, исправить его до аварийных сценариев.

1. ПЕРЕЗАГРУЗИТЬ ОБЕ МАШИНЫ И ПРОВЕРИТЬ АВТОЗАПУСК
-------------------------------------------------
Campus DB:

sudo reboot

Дождаться загрузки, войти в консоль. Если использовался SSH, подключиться заново.

hostname
systemctl is-enabled postgresql
systemctl is-active postgresql
pg_lsclusters

Ожидается: campus-db, enabled, active, online.
Только после готовности БД перезагрузить Campus App:

sudo reboot

После загрузки и входа на Campus App:

hostname
systemctl is-enabled campus
systemctl is-active campus
curl -i --max-time 15 http://127.0.0.1:8000/health

Ожидается: campus-app, enabled, active, HTTP 200.
В браузере Mac открыть http://172.16.114.10:8000 и проверить сохранённые записи.
Не запускать Python вручную: в этом пункте проверяется автозапуск systemd.

2. ОСТАНОВИТЬ БД И ПРОДИАГНОСТИРОВАТЬ ПРИЛОЖЕНИЕ
-----------------------------------------------
Campus DB:

sudo systemctl stop postgresql
pg_lsclusters

Ожидается: кластер down.
Campus App:

curl -i --max-time 15 http://127.0.0.1:8000/health
systemctl status campus --no-pager
sudo journalctl -u campus -n 30 --no-pager

Ожидается: HTTP 503, ошибка доступа к БД в журнале.
campus может оставаться active: процесс жив, но зависимость недоступна.
HTTP 503 нельзя путать с полным отсутствием HTTP-соединения.

Восстановление, Campus DB:

sudo systemctl start postgresql
pg_lsclusters

Campus App:

curl -i --max-time 15 http://127.0.0.1:8000/health

Ожидается: online и HTTP 200 без ручного перезапуска приложения.

3. НАЙТИ ПРОЦЕСС, ПОРТ И ЖУРНАЛЫ
-------------------------------
Campus App:

systemctl show campus -p MainPID -p User -p Restart
ps -ef | grep '[g]unicorn'
sudo ss -lntp '( sport = :8000 )'
sudo journalctl -u campus -n 20 --no-pager

Показать: MainPID, User=campusapp, Restart=on-failure,
процессы Gunicorn, слушающий порт 8000 и записи запросов в журнале.
Выход из постраничного просмотра systemctl/journalctl, если он открылся: q.

Campus DB:

pg_lsclusters
sudo ss -lntp '( sport = :5432 )'
sudo systemctl status postgresql --no-pager

postgresql.service — общий unit; его active само по себе не доказывает,
что конкретный кластер принимает подключения. Поэтому нужен pg_lsclusters.

4. ИЗМЕНИТЬ ПАРАМЕТР СЛУЖБЫ И ВОССТАНОВИТЬ
-----------------------------------------
Campus App. До изменения записать исходное RestartUSec:

systemctl cat campus
systemctl show campus -p RestartUSec
sudo test ! -e /etc/systemd/system/campus.service.d/defense-demo.conf

Последняя команда должна завершиться успешно (код 0).
Если файл уже существует, не перезаписывать и не удалять его:
сначала выяснить назначение или выбрать другое уникальное имя для демо.
В базовом unit проекта RestartSec=3s; реальные переопределения могут отличаться.

sudo systemctl edit --drop-in=defense-demo.conf campus

В редакторе вписать в разрешённую область перед служебной границей:

[Service]
RestartSec=10s

Сохранить и выйти. Если открылся nano: Ctrl+O, Enter, Ctrl+X.
Если открылся vi/vim: i для ввода, затем Esc и :wq с Enter.

sudo systemctl daemon-reload
sudo systemctl restart campus
systemctl show campus -p RestartUSec
curl -i --max-time 15 http://127.0.0.1:8000/health

Ожидается: RestartUSec=10s и HTTP 200.

Восстановление — удалить ТОЛЬКО созданный нами временный файл:

sudo rm /etc/systemd/system/campus.service.d/defense-demo.conf
sudo systemctl daemon-reload
sudo systemctl restart campus
systemctl show campus -p RestartUSec
curl -i --max-time 15 http://127.0.0.1:8000/health

Ожидается: исходное записанное значение RestartUSec, HTTP 200.
Не применять systemctl revert: он может удалить другие переопределения.

5. ПРОВЕРИТЬ НЕДОСТУПНОСТЬ БД С ПОСТОРОННЕГО УЗЛА
-----------------------------------------------
БД должна быть запущена, кластер online.
Campus App — разрешённый узел:

nc -vz -w 3 172.16.114.20 5432

Ожидается: successful/succeeded, TCP-соединение устанавливается.

Mac — третий узел, НЕ Campus App и НЕ сама Campus DB:

nc -vz -G 3 172.16.114.20 5432

Ожидается: timeout или отказ, соединение не устанавливается.
Mac использует -G для ограничения времени соединения; Linux — -w.
Если проверка с Campus App тоже не проходит, это ещё не доказательство изоляции:
проверить БД, сеть и firewall. Если с Mac проходит — изоляция не выполнена.

Campus DB — показать правила и конфигурацию:

sudo ufw status numbered
sudo -u postgres psql -Atc 'show listen_addresses; show hba_file;'
sudo grep -n 'campus_app' /etc/postgresql/*/main/pg_hba.conf

Ожидается: UFW активен; 5432 разрешён от 172.16.114.10,
нет общего разрешения 5432 для любых адресов/всей клиентской сети.
pg_hba ограничивает подключение роли приложения адресом сервера приложения.
Положительный контроль с Campus App и отрицательный с Mac выполняются подряд,
при одинаковом работающем состоянии БД.
