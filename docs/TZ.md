## 1 Введение

Программа предназначена для учёта аудиторного фонда университета: корпусов,
закреплённых за подразделениями помещений, их площади и объёма. Минимальная
версия разрабатывается в ЛР1 и является основой единого сквозного проекта.

ТЗ оформлено как электронный текст в репозитории с разделами ГОСТ 19.201-78.
Источник структуры: [ГОСТ 19.201-78 в фонде Росстандарта](https://protect.gost.ru/gost/details/b64061cf-6bb2-4c75-aee9-18bb5e26e554),
[текст стандарта](https://www.swrit.ru/doc/espd/19.201-78.pdf).
Бумажный лист утверждения и подписи оформляются при необходимости по требованиям
преподавателя; наличие подписанного бумажного документа не заявляется.

## 3 Назначение разработки

Функциональное назначение — заменить разрозненный ручной список единым
связанным справочником с проверкой целостности данных.
Эксплуатационное назначение — демонстрация и локальная работа сотрудника
на одном компьютере через браузер.

Категории пользователей по предметной области:

- Сотрудник хозяйственной службы создаёт и изменяет корпуса и помещения.
- Представитель подразделения просматривает закреплённые помещения.
- Руководитель просматривает площади и рассчитанные объёмы.

В версии ЛР1 эти категории описывают сценарии, а не права доступа: вход,
учётные записи и разграничение полномочий не реализуются. Все операции доступны
локальному пользователю. Программа не предназначена для открытого доступа в сети.

Основной сценарий: создать корпус → создать подразделение → добавить помещение
с привязкой к обоим справочникам → просмотреть объём → изменить характеристики.
Удаление выполняется в обратном порядке зависимостей; используемые записи
справочников защищены от удаления.

## 4 Требования к программе

### 4.1 Функциональные характеристики

Ф1. Предоставить создание, список, чтение по ID, полное изменение и удаление
корпусов, подразделений и помещений через HTTP API. В браузере предоставить
таблицы и формы для тех же операций.

Ф2. Корпус хранит ID, название и адрес. Подразделение — ID и название.
Помещение — ID, корпус, подразделение, номер, площадь в м² и высоту в метрах.
Связи: один корпус содержит много помещений; одно подразделение отвечает
за много помещений. Каждое помещение ссылается ровно на один существующий
корпус и ровно на одно существующее подразделение.

Ф3. Номер помещения уникален в пределах корпуса. Один и тот же номер в разных
корпусах разрешён. Названия корпусов и подразделений уникальны в своих таблицах.
Сравнение строк регистрозависимое, пробелы по краям удаляются до сохранения.

Ф4. Площадь: конечное число в интервале (0; 100000] м², высота — (0; 100] м.
Верхние границы — ограничения ввода учебной системы, а не строительные нормативы.
Объём = площадь × высота, возвращается с округлением до двух знаков;
не хранится отдельно и не принимается от клиента.

Ф5. Удаление корпуса/подразделения при наличии помещений запрещено.
Перенос помещения в другой корпус/подразделение допустим через изменение
с проверкой существования родителей и уникальности номера.

Ф6. Ограничения строк: название 1–100, адрес 1–250, номер 1–30 символов
после удаления крайних пробелов. ID — положительное целое в диапазоне SQLite.
Обязательны все поля; неизвестные поля, null, неверные типы и пустые значения
отклоняются. POST и PUT принимают JSON-объект размером до 16 КиБ.

Ф7. Ошибки API возвращаются в JSON с полем `error`: 400 — некорректные данные,
404 — неизвестный ресурс/запись, 405 — неподдерживаемый метод, 409 — конфликт
уникальности или ссылок, 413 — слишком большое тело, 415 — неверный Content-Type,
503 — недоступна БД. Успех: 200, создание: 201, удаление: 204.
Интерфейс показывает ошибки пользователю, не подставляя ввод как HTML.

Ф8. `/health` возвращает 200 и состояние БД при успешном чтении всех трёх таблиц,
503 при ошибке БД. Путь к БД, адрес и порт сервера задаются окружением.

### 4.2 Надёжность и хранение данных

Данные хранятся в файле SQLite. Таблицы создаются при первом запуске без
перезаписи данных. Сохранённые записи должны переживать перезапуск приложения.
Каждое изменение выполняется в транзакции; ошибка не оставляет частичных данных.
Внешние ключи включаются на каждом соединении, уникальность и диапазоны
дублируются SQL-ограничениями. SQL-значения передаются параметрами.

Объём вычисляется на чтении, чтобы не хранить противоречащие площади значения.
Используется REAL: допустимо обычное округление чисел с плавающей точкой,
поскольку система не выполняет финансовые расчёты.
После штатной остановки достаточно снова запустить сервер. Восстановление после
потери диска, регламент резервных копий и инфраструктурная отказоустойчивость
не входят в ЛР1. Автоматическое обновление схемы будущих версий здесь не реализуется.

### 4.3 Условия эксплуатации

Локальная учебная работа в macOS/Linux, один запущенный процесс приложения.
Для работы нужен пользователь, умеющий пользоваться браузером; для установки —
участник команды, владеющий Python, терминалом и Git. SQLite допускает
последовательное выполнение записей; при длительной блокировке возвращается 503.

### 4.4 Технические средства

Обычный учебный компьютер с Python 3.9 или новее, Git и Make, 1 ГБ свободной
оперативной памяти и 300 МБ свободного диска для окружения и небольшого справочника.
Браузер с поддержкой Fetch API. Интернет нужен для первоначальной установки
зависимостей и удалённого Git-процесса; для локальной работы не требуется.
Численные требования к производительности и нагрузочные испытания в ЛР1 не заданы.

### 4.5 Информационная и программная совместимость

Flask, SQLite из стандартной библиотеки Python, HTML/CSS/JavaScript без сборщика.
Кодировка UTF-8, обмен JSON по HTTP. Версии прямых зависимостей закреплены
в `requirements*.txt`. Подробный контракт — `docs/API.md`, схема — `docs/DATA.md`.

### 4.6 Маркировка и упаковка

Исходный код передаётся единым Git-репозиторием `Project_DevOps`.
Первая версия маркируется аннотированным тегом `v0.1.0`.
Локальная БД и виртуальное окружение не входят в поставку.

### 4.7 Транспортирование и хранение

Передача — клонирование репозитория. Хранение исходников — локально и на
GitHub/GitLab после публикации пользователем. Специальных требований к физическим
носителям нет. Локальные данные хранятся отдельно в `instance`.

### 4.8 Специальные требования

Не коммитить секреты и `.env`, не включать debug-режим по умолчанию.
Не реализовывать Docker, CI/CD, очереди и мониторинг следующих лабораторных заранее.
Все изменения проходят проверки по `CONTRIBUTING.md`.

## 6 Технико-экономические показатели

Учебная разработка команды из трёх человек. Коммерческая стоимость и годовой
экономический эффект не рассчитываются; сравнение с коммерческими аналогами
не требуется. Практическая польза — уменьшение дублирования записей и ошибок связей.
Платные сервисы и лицензии для локальной работы не требуются.

## 7 Стадии и этапы разработки

1. Подготовить задачу и ТЗ в рамках ЛР1.
2. Реализовать БД и API, затем веб-интерфейс в ветке функции.
3. Добавить проверки, исправить обнаруженные ошибки и оформить документацию.
4. Воспроизвести конфликт и документировать разрешение.
5. Опубликовать задачу и PR, пройти проверку другим участником, отметить версию тегом.
6. Провести защиту с контрольным изменением.

Срок — сдача ЛР1 по расписанию преподавателя, конкретная дата не предоставлена.
Исполнители — команда, указанная на титуле; распределение ответственности
утверждается командой. Фактическое авторство не подменяется чужими Git-учётными данными.

## 8 Порядок контроля и приёмки

Автоматическая проверка: `make verify` — Ruff, форматирование, pytest и проверка diff.
Тесты должны покрывать CRUD, правила предметной области, неверные запросы,
целостность БД, сохранение после повторного создания приложения и `/health`.

Демонстрация: создать корпус и подразделение, добавить помещение 40.5 м² × 3.2 м,
получить объём 129.6 м³; изменить характеристики и увидеть новый объём.
Показать отказ на дубликате номера, отрицательной площади и удалении используемого
справочника. После удаления помещения справочник должен удаляться.

Организационная приёмка: показать Issue → ветку → несколько коммитов → PR/MR →
проверку другим участником → слияние → тег, реальный конфликт и его разрешение,
исключение локальных файлов из Git. На защите выполнить отдельное небольшое
изменение через новую задачу, ветку и PR. Без внешних действий работа по Git-процессу
не считается полностью принятой. Перечень открытых пунктов — `docs/LR1-CHECKLIST.md`.
