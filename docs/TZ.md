## 2. Назначение и цели создания продукта

Приложение предназначено для ведения справочника корпусов, подразделений и
помещений университета через веб-интерфейс и HTTP API.

Цели разработки:

- Хранить сведения о помещениях в единой реляционной базе данных.
- Связать каждое помещение с корпусом и ответственным подразделением.
- Исключить повторение номера помещения внутри одного корпуса.
- Рассчитывать объём помещения по площади и высоте без ручного ввода результата.
- Обеспечить воспроизводимую установку, запуск и проверку приложения.
- Организовать внесение изменений через задачи, ветки, review и версии в Git.

## 3. Характеристика объекта автоматизации

Объект автоматизации — учёт аудиторного фонда университета. В справочнике
хранятся названия и адреса корпусов, названия подразделений, номера и размеры
помещений. Помещения одного корпуса могут закрепляться за разными
подразделениями; подразделение может отвечать за помещения в разных корпусах.

Пользователи справочника — сотрудники, которые ведут сведения о помещениях
и просматривают актуальные записи. Разработчики сопровождают приложение и
проверяют изменения. Эти категории описывают участников процесса, а не
отдельные роли доступа: регистрация, вход и разграничение прав в ЛР1 не входят.

Основной сценарий: пользователь создаёт корпус и подразделение, добавляет
связанное с ними помещение, просматривает его размеры и рассчитанный объём.
При изменении данных пользователь редактирует запись. Для удаления корпуса
или подразделения сначала удаляются либо переназначаются связанные помещения.

## 4. Требования к продукту

### 4.1. Структура и функционирование

Приложение должно включать HTTP-сервер, реляционную базу данных и веб-интерфейс.
Интерфейс и API должны работать с одними и теми же данными и правилами проверки.
Начальное состояние базы может быть пустым; обязательное предварительное
заполнение не требуется.

Для ЛР1 используются Python 3.9 или новее, Flask и SQLite. Интерфейс реализуется
на HTML, CSS и JavaScript и открывается в браузере через адрес сервера.
Открытие HTML-шаблона как локального файла не является способом запуска.

### 4.2. Функциональные требования

- **Ф-01. Корпуса:** создание, просмотр списка и отдельной записи,
  редактирование названия и адреса, удаление.
- **Ф-02. Подразделения:** создание, просмотр списка и отдельной записи,
  редактирование названия, удаление.
- **Ф-03. Помещения:** создание, просмотр списка и отдельной записи,
  редактирование корпуса, подразделения, номера, площади и высоты, удаление.
- **Ф-04. Расчёт объёма:** объём в м³ вычисляется как площадь в м² × высота
  в метрах; результат округляется до двух знаков после запятой.
  Объём не вводится пользователем и не хранится отдельным столбцом.
- **Ф-05. Веб-интерфейс:** отдельные разделы для трёх справочников, формы
  добавления и редактирования, выбор корпуса и подразделения из существующих
  записей, вывод результата операций и сообщений об ошибках.
- **Ф-06. Проверка работоспособности:** `GET /health` проверяет доступ к базе;
  при исправной работе возвращает HTTP 200, при ошибке базы — HTTP 503.

### 4.3. Данные и ограничения

| Сущность | Обязательные данные |
|---|---|
| Корпус | ID, уникальное название, адрес |
| Подразделение | ID, уникальное название |
| Помещение | ID, корпус, подразделение, номер, площадь, высота |

ID присваивает база данных. Каждое помещение связано ровно с одним корпусом
и одним подразделением внешними ключами. У корпуса и подразделения может
не быть помещений. Подробная схема приведена в [DATA.md](DATA.md).

Обязательные правила:

1. Пара «корпус — номер помещения» уникальна. Одинаковые номера в разных
   корпусах допустимы.
2. Названия корпусов и подразделений уникальны внутри своего справочника.
   Сравнение строк регистрозависимое.
3. Название содержит от 1 до 100 символов, адрес — от 1 до 250,
   номер помещения — от 1 до 30. Крайние пробелы удаляются; пустые строки запрещены.
4. Площадь: `0 < area ≤ 100000`; высота: `0 < height ≤ 100`.
   Числовые строки, логические значения, NaN и Infinity не принимаются как размеры.
5. ID связанного корпуса и подразделения — положительные целые числа,
   соответствующие существующим записям.
6. Удаление используемого корпуса или подразделения запрещено.
   Каскадное удаление помещений не выполняется.
7. Ошибка создания или изменения не должна приводить к частичной записи
   или повреждению ранее сохранённых данных.

### 4.4. HTTP API и обработка ошибок

API предоставляет операции `GET`, `POST`, `PUT`, `DELETE` для ресурсов
`/api/buildings`, `/api/departments`, `/api/rooms`. Работа с отдельной записью
выполняется по пути `/{id}`. `PUT` заменяет все изменяемые поля записи.
Списки возвращаются по возрастанию ID.

Тела `POST` и `PUT` передаются в JSON и должны содержать полный набор разрешённых
полей. Неизвестные поля запрещены. Максимальный размер тела запроса — 16 КиБ.
Ошибки возвращаются в формате `{"error":"Описание причины"}`.

| Ситуация | HTTP-код |
|---|---|
| Успешное чтение или редактирование | 200 |
| Создание записи | 201 |
| Удаление записи | 204 |
| Некорректные данные или JSON | 400 |
| Отсутствующая запись или адрес | 404 |
| Неподдерживаемый метод | 405 |
| Нарушение уникальности или связей | 409 |
| Превышение размера запроса | 413 |
| Неверный Content-Type при записи | 415 |
| Ошибка доступа к базе данных | 503 |

Состав полей, примеры запросов и ответов определены в [API.md](API.md).

### 4.5. Надёжность, безопасность и условия эксплуатации

Данные сохраняются в файле SQLite и остаются доступными после перезапуска.
Первый запуск создаёт отсутствующие таблицы; повторный запуск не очищает базу.
Изменения выполняются в транзакциях. SQL-запросы используют параметры;
пользовательский текст в интерфейсе не должен исполняться как HTML или JavaScript.

Локальный запуск по умолчанию доступен только на `127.0.0.1:8000`.
Адрес, порт и путь к базе задаются переменными `APP_HOST`, `APP_PORT`,
`DATABASE_PATH`. Пример конфигурации хранится в `.env.example`.
Рабочая `.env`, базы, журналы, виртуальное окружение и секреты исключаются из Git.

Публичное размещение без дополнительных средств защиты не предусматривается:
в приложении нет аутентификации и разграничения доступа. Требования к отказоустойчивому
кластеру, высокой нагрузке и гарантированному времени ответа в ЛР1 не устанавливаются.

Пользовательский интерфейс и документация должны быть на русском языке.
Технические имена полей API и идентификаторы кода — на английском.

## 6. Порядок контроля и приёмки системы

### 6.1. Предварительные проверки

Перед передачей изменений выполняется `make verify`. Все автоматические
проверки должны завершиться успешно. Автотесты используют отдельную временную
базу и не изменяют рабочий справочник. Пропуск или отключение проверок ради
успешного результата не допускается.

Автотесты проверяют CRUD трёх сущностей, расчёт объёма, ограничения полей,
уникальность, связи, обработку ошибочных запросов, откат изменений,
сохранность данных и служебный адрес. Внешний вид и действия пользователя
проверяются отдельно в браузере.

### 6.2. Приёмочные сценарии

1. Установить зависимости по README, запустить приложение, открыть `/`.
2. Создать два корпуса и одно подразделение через интерфейс.
3. Добавить помещение площадью 40 м² и высотой 3 м. Получить объём 120 м³.
4. Проверить чтение, редактирование и удаление для каждого справочника.
5. Попробовать повторить номер в том же корпусе: получить отказ без записи.
   Добавить такой номер в другом корпусе: получить успешный результат.
6. Попробовать сохранить пустое название, нулевую площадь и отсутствующего
   родителя: получить ошибку, убедиться, что данные не изменились.
7. Попробовать удалить корпус или подразделение с помещением: получить отказ.
8. Перезапустить приложение и убедиться в сохранении ранее созданных записей.
9. Проверить успешный ответ `/health` и соответствие ответов API документации.
10. Проверить состав репозитория, отсутствие секретов, правила внесения изменений
    и историю работы над функцией, включая review и разрешение конфликта.

Перед выпуском проводится пробная работа со справочниками на тестовых данных.
Критерий готовности — выполнение функциональных требований и приёмочных
сценариев без ошибок, успешные локальные проверки и наличие документации.
При выявлении дефекта создаётся задача, выполняется исправление и повторная
проверка затронутого сценария. Приёмка завершается не позднее срока сдачи ЛР1
по календарному графику курса.

Поставка включает исходный код, файлы зависимостей, конфигурационный пример,
тесты и документацию. Виртуальное окружение и рабочая база в поставку не входят.
