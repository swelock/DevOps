# Завершение Git-процесса ЛР1

## Что уже сделано локально

Git-репозиторий расположен в `Project_DevOps`, а не в родительском каталоге курса.
`main` содержит первоначальную постановку `LR1-01` (`00dbed4`).
В `feature/lr1-campus` выполнена функция несколькими содержательными коммитами:
API/БД, веб-интерфейс, тесты и исправления, документация.
Конфликт с `docs/room-metrics` разрешён настоящим merge-коммитом `1b28c21`.

После локальной проверки создан аннотированный тег `v0.1.0`.
Он фиксирует локальный проверенный снимок ветки функции. Это ещё не принятый
командой удалённый релиз: `main` намеренно не объединена с функцией без PR.
Все коммиты созданы под уже настроенным локальным Git-автором.

Удалённого origin, Issue, PR и review другого участника пока нет.
В окружении не обнаружены GitHub/GitLab-коннектор и `gh`; удалённый адрес
пользователь не предоставлял. Ниже подготовлен полный порядок ручных действий.
Не выдавайте перенос локальной задачи в Issues за её создание на GitHub до разработки:
реальная предварительная постановка сохранена в первом локальном коммите.

## Публикация

1. В своём GitHub/GitLab создайте пустой репозиторий `Project_DevOps`.
   Не создавайте там README/.gitignore, чтобы не получить независимую историю.
   Добавьте остальных участников команды и доступ преподавателю по требованиям курса.
2. В терминале внутри `Project_DevOps` выполните, заменив `YOUR_ACCOUNT`
   на свой аккаунт (для GitLab используйте URL, показанный вашим сервером):

```bash
git remote add origin https://github.com/YOUR_ACCOUNT/Project_DevOps.git
git push -u origin main
git push -u origin feature/lr1-campus
git push origin docs/room-metrics
```

3. Создайте Issue: заголовок и текст из `docs/issues/LR1-01.md`.
   Укажите, что до публикации задача велась локально, и ссылку на коммит `00dbed4`.
4. Откройте PR/MR из `feature/lr1-campus` в `main`, описание — `docs/PR-LR1.md`.
   Укажите фактическую ссылку на Issue. При необходимости добавьте `Closes #N`
   с настоящим номером задачи.
5. Другой участник клонирует ветку, выполняет `make setup`, `make verify`,
   проверяет веб-интерфейс и diff; фиксирует результат review в PR.
   Одобрение от имени другого человека автоматически не создавалось.
6. После исправления замечаний и повторных проверок выполните обычный
   **Merge pull request / merge commit**, сохранив коммиты и учебный конфликт.
   Не используйте squash/rebase для этой первой учебной истории.
7. Получите принятую ветку и опубликуйте тег:

```bash
git switch main
git pull --ff-only origin main
make verify
git merge-base --is-ancestor v0.1.0 main
git diff v0.1.0 main
git push origin v0.1.0
```

`merge-base` должен завершиться с кодом 0, `git diff` — быть пустым, если при
review код не менялся. В этом случае тег проверенного коммита входит в `main`.
Если review потребовал правок, не публикуйте старый тег как исправленную версию:
сохраните `v0.1.0` как исходный снимок, а принятые исправления отметьте `v0.1.1`
после проверки. Не перемещайте уже опубликованные теги.

Для защищённой `main` настройте запрет прямой записи и обязательный review, если
ваш тариф и правила курса это позволяют. Workflow CI в ЛР1 не создаётся.

## Контрольное изменение на защите

Создайте новую Issue, например «Уточнить подсказку поля площади».
Из принятой актуальной `main`:

```bash
git switch main
git pull --ff-only
git switch -c docs/room-area-hint
# Измените подсказку в campus/static/app.js и проверьте её в браузере.
make verify
git diff
git add campus/static/app.js
git commit -m "docs: clarify room area units in form"
git push -u origin docs/room-area-hint
```

Откройте новый PR с новой задачей, покажите diff и проверку другим участником.
Это живое действие на защите, заранее вместо него пустой коммит не создаётся.
