# Аудиторный фонд университета

Приложение для учёта корпусов, подразделений и помещений университета.
Для помещения сохраняются площадь, высота и вместимость; объём рассчитывается автоматически.
Номер уникален в пределах корпуса. Удаление корпуса или подразделения со связанными
помещениями запрещено.

Проект по дисциплине DevOps, тема №9, группа 241-353.
Команда: Ильин Кирилл Александрович, Исламов Евгений Русланович,
Турбабин Вадим Дмитриевич.

## Стек

Flask, HTML/CSS/JavaScript без сборщика, SQLite для разработки и PostgreSQL
для Linux-стенда. На сервере приложение работает через Gunicorn под управлением
systemd. Основной стенд работает без контейнеров; Docker Compose доступен для локального запуска.

## Локальный запуск

Команды выполняются из корня репозитория:

```bash
make setup
make verify
.venv/bin/flask --app campus create-user operator
make run
```

Файл `.env` создаётся только при первой настройке; существующая конфигурация
сохраняется. Требуется Python 3.9+; установка зависимостей требует подключения
к интернету.

Адрес: `http://127.0.0.1:8000`. При занятом порту можно выбрать другой свободный
порт: `APP_PORT=8012 make run`. Остановка локального сервера — Ctrl+C.
Интерфейс открывается через HTTP, а не напрямую из `campus/templates/index.html`.

`make setup` создаёт `.venv`, устанавливает закреплённые зависимости, создаёт `.env`
со случайным `SECRET_KEY` и применяет миграции. Повторный запуск сохраняет
существующую конфигурацию и данные. Готового пароля пользователя нет.

Команда `create-user operator` попросит пароль дважды. Ввод скрыт — это нормально.
Используйте 10–128 символов. Готового общего пароля нет. Откройте приложение,
введите логин `operator` и выбранный пароль. Кнопка «Выйти» завершает сеанс.
Все вошедшие пользователи имеют одинаковый доступ к справочникам.

Первый запуск создаёт пустую SQLite. Сначала добавляются корпус и подразделение,
затем помещение. Записи сохраняются после перезапуска.

## Конфигурация

`run.py` и команды обслуживания загружают `.env`. Переменные процесса имеют приоритет над файлом.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_HOST` | `127.0.0.1` | Адрес HTTP-сервера |
| `APP_PORT` | `8000` | Порт HTTP |
| `DATABASE_ENGINE` | `sqlite` | `sqlite` или `postgresql` |
| `DATABASE_PATH` | `instance/campus.sqlite3` | SQLite-файл относительно корня проекта |

Для PostgreSQL используются `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`,
`DATABASE_USER` и `DATABASE_PASSWORD`. На Linux они хранятся отдельно от исходников
в `/etc/campus/campus.env`, права — `root:campusapp 0640`.
Рабочие пароли, приватные ключи и локальные базы в Git не входят.

## Linux-стенд

Две Ubuntu Server 24.04 ARM64 в NAT-сети VMware Fusion `172.16.114.0/24`:

| Узел | Адрес | Служба |
|---|---|---|
| `campus-app` | `172.16.114.10` | `campus.service`, HTTP 8000 |
| `campus-db` | `172.16.114.20` | PostgreSQL, порт 5432 только для сервера приложения |

Интерфейс стенда: `http://172.16.114.10:8000`.
Администрирование — SSH по ключу под `devopsadmin`; Gunicorn работает от `campusapp`.
Пользователи входят по логину и паролю; API также требует сеанс.
HTTPS на текущем стенде не настроен. Стенд рассчитан на внутреннюю сеть.
Сеанс действует до 8 часов, cookie имеет HttpOnly и SameSite=Lax.
`SECRET_KEY` обязателен, минимум 32 символа; при HTTPS задайте
`SESSION_COOKIE_SECURE=true`, при локальном HTTP оставьте `false`.

## Проверки

- `make setup` — окружение, конфигурация с ключом сессий, миграции.
- `make run` — локальный HTTP-сервер.
- `make test` — unit, интеграционные SQLite и HTTP-тесты; порог покрытия 80%.
- `make quality` — Ruff lint/format и SAST Bandit.
- `make migrate` — обновление БД до последней миграции Alembic.
- `make backup` — новая копия в `backups/`; путь можно задать `FILE=...`.
- `make restore FILE=backups/имя.sqlite3` — восстановление при остановленном приложении.
- `make mutation-check` — четыре контрольные поломки во временной копии.
- `make verify` — последовательно quality, test, mutation-check, deploy-check, diff.
- `make format` — исправление форматирования, после него нужен `make verify`.
- `make up`, `make down`, `make container-check` — локальный контейнер и проверка /health.
- `make postgres-check` — реальные проверки на временных PostgreSQL БД на DB VM от postgres.

`make verify` не изменяет рабочую БД. Тесты создают временные файлы SQLite;
PostgreSQL-проверка отдельно создаёт две временные БД и удаляет их после прогона.
Пропуски и xfail в обязательном прогоне считаются ошибкой.
JUnit: `reports/tests.xml`; покрытие: `reports/coverage.xml` и `reports/htmlcov/index.html`;
SAST: `reports/bandit.json`; мутации: `reports/mutations.json`. Отчёты, копии и БД исключены из Git.
Порядок миграций и восстановления: [OPERATIONS.md](docs/OPERATIONS.md).

Для контейнера сначала выполняется `make setup`, затем `make up` и
`make container-check`. Пользователь создаётся командой
`docker compose exec app flask --app campus create-user operator`.
Если порт 8000 занят, используется `CONTAINER_PORT=8013 make up`.
Данные находятся в именованном томе; `make down` сохраняет его.

## Логирование

Приложение пишет метод, путь и код ответа каждого запроса; ошибки БД и
неожиданные ошибки — с traceback. Успешный вход, отказ во входе и выход также
фиксируются. Пароли, тела запросов, cookie и CSRF-токены в эти записи не добавляются.
При `make run` записи видны в терминале. На Linux:
`sudo journalctl -u campus -n 50 --no-pager`.
Журналы Gunicorn направлены в systemd journal. `/health` проверяет четыре таблицы,
включая пользователей, и доступен без входа.

### 3. Назначение разработки

Система заменяет разрозненные списки единым справочником. Сотрудник хозяйственной
службы ведёт корпуса и помещения; представитель подразделения и руководитель
просматривают закреплённые помещения и их характеристики. В учебной версии
все учётные записи обладают одинаковыми правами; отдельные роли не реализуются.
Администратор создаёт учётные записи локальной CLI-командой.
Основной сценарий: вход → корпус → подразделение → помещение → просмотр
рассчитанного объёма → изменение или удаление → выход.

### 4. Требования к программе

Функции: создание, список, чтение по ID, полное изменение и удаление трёх
связанных сущностей через HTTP API и браузер. Пользователь хранит ID, уникальный
логин и хеш пароля; публичной регистрации нет. Вход по логину и паролю создаёт
подписанную сессию до 8 часов; выход очищает её. Без входа интерфейс перенаправляет
на `/login`, API справочников возвращает 401. Изменяющие запросы, включая вход
и выход, требуют CSRF-токен, иначе 403. Пароль: 10–128 символов при создании,
логин: 1–100 после обрезки пробелов. Хеширование — PBKDF2-SHA256 со случайной солью.

Помещение ссылается на существующие корпус и подразделение. Номер уникален
в пределах корпуса. Удаление используемого корпуса или подразделения запрещено.
Объём вычисляется как площадь × высота и округляется до двух знаков.
Названия: 1–100 символов, адрес: 1–250, номер: 1–30.
Площадь: 0 < значение ≤ 100000 м², высота: 0 < значение ≤ 100 м.
Неизвестные поля, неверные типы, нечисловые значения и пустые строки отклоняются.
POST/PUT используют JSON, тело не более 16 КиБ. Контракт и коды ошибок — в `docs/API.md`.

Хранение: SQLite локально, PostgreSQL на Linux-стенде. Связи защищены внешними
ключами, уникальность и диапазоны — SQL-ограничениями. Запросы параметризованы,
изменения выполняются в транзакциях, данные сохраняются после перезапуска.
SQLite применяет миграции Alembic без удаления записей.
PostgreSQL-схему обновляет администратор, приложение не получает DDL-права.
Миграции 001 → 002 → 003 создают исходную схему, индексы связей и вместимость.
Вместимость — целое число от 1 до 1000; старые записи получают 1.
В API отсутствие capacity совместимо со старым клиентом и означает 1, в том числе при PUT.

`/health` без входа проверяет чтение четырёх таблиц: 200 при успехе, 503 при ошибке.
Ошибки БД и неожиданные ошибки журналируются с traceback; клиенту возвращается
безопасное сообщение. Логи доступны в терминале или systemd journal.
Конфигурация БД, адреса, порта и ключа сессий задаётся окружением; локально — `.env`.
Секреты и локальные БД исключены из Git. Debug выключен.

Среда: Python 3.9+, Flask, Git, Make, браузер с Fetch API; HTML/CSS/JavaScript
без сборщика. Учебный компьютер: ориентировочно 1 ГБ свободной памяти и 300 МБ
диска для локальной версии. Версии основных зависимостей закреплены в requirements-файлах,
транзитивных — в `requirements-lock.txt` (pip constraints).
Эксплуатация — локальный компьютер или внутренняя сеть учебного Linux-стенда.
При HTTPS включается Secure cookie. Публичное размещение не входит в эту редакцию.
Передача — Git-репозиторий; первая версия отмечена `v0.1.0`, последующие получают
новые теги. Локальные БД, секреты и виртуальное окружение в поставку не входят.
