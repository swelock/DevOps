# Правила внесения и приёмки изменений

## GitFlow

- `main` содержит принятые выпуски, `develop` — подготовку следующего выпуска.
- `feature/<номер>-<суть>` создаётся от `develop` и объединяется через PR в `develop`.
- `release/<версия>` создаётся от `develop`. После проверок и review объединяется
  через PR в `main`; на принятом коммите создаётся аннотированный тег версии.
  Изменения выпуска также объединяются в `develop`.
- `hotfix/<номер>-<суть>` создаётся от `main` для срочного исправления выпуска.
  После проверок и review объединяется в `main` с новым тегом и в `develop`.
- Слияния выполняются с сохранением коммитов (Create a merge commit).

## Порядок внесения изменений

1. Сначала задача: что меняем, зачем, как проверим. Одна функция — одна feature-ветка.
2. Делаем небольшие понятные коммиты. В сообщении пишем смысл, а не «1» или «update».
3. До PR и после исправления замечаний выполняем `make verify` и затронутый
   сценарий в браузере. Проверки нельзя отключать, чтобы получить зелёный результат.
4. В PR другой участник смотрит diff, повторяет проверки и оставляет review.
   Самопроверка автора не заменяет независимую проверку.
5. Используем Create a merge commit, чтобы сохранить отдельные коммиты.
6. В main попадает проверенный выпуск. Тег ставим на принятый коммит main.
7. Не коммитим `.env`, пароли, ключи, БД, логи, `.venv` и кэши. Не делаем force push,
   не переписываем общую историю и не передвигаем опубликованные теги.
8. Конфликт читаем с обеих сторон и сохраняем нужные изменения. После решения
   снова запускаем проверки.

Обязательные команды:

```bash
make verify
git diff --check
git status --short
git diff --stat
```

`make verify` запускает Ruff, проверку форматирования, pytest, синтаксис deploy-скриптов,
поиск явных секретов и `git diff --check`. Это не доказательство отсутствия любых секретов:
перед коммитом также читаем `git diff --cached`. `make format` исправляет форматирование,
но после него снова требуется `make verify`.

Рецензент сверяет задачу, ТЗ в README, API, ограничения БД, UI, тесты и отсутствие
секретов. Особое внимание: Makefile, tests, pyproject.toml, requirements, .gitignore
и правила приёмки. Их изменения нельзя ослаблять без понятного обоснования.
Неуспешная проверка — исправить причину, повторить проверку и review.

## Секреты и локальные файлы

Перед коммитом проверяются исключения и состав отслеживаемых файлов:

```bash
git check-ignore -v .env .env.local instance/campus.sqlite3 .venv/bin/python
git ls-files -- .env '.env.*' '*.sqlite*' '*.db' '*.log' '*.key' '*.pem' '.venv/*'
git diff --cached
```

В Git допускается безопасный `.env.example` без рабочих секретов.
`.gitignore` не исключает файлы, которые уже отслеживаются. При публикации секрета
его необходимо отозвать; удаления строки следующим коммитом недостаточно.
