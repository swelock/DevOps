# Правила внесения и приёмки изменений

## Порядок работы

1. Создать задачу с целью, критериями приёмки и способом проверки.
2. От актуальной `main` создать ветку `feature/<номер>-<суть>` или `fix/<номер>-<суть>`.
3. Вносить небольшие логичные изменения; делать осмысленные коммиты.
4. Выполнить `make verify`, проверить `git diff` и работу затронутого сценария в браузере.
5. Отправить ветку, открыть PR/MR в `main`, связать его с задачей.
6. Другой участник читает diff, воспроизводит проверки, фиксирует результат в review.
7. Устранить замечания, повторить проверки, получить одобрение и слить PR.
8. Версию отметить аннотированным тегом; публиковать только проверенный результат.

Команды перед PR и после разрешения конфликта:

```bash
make verify
git diff --check
git status --short
git diff --stat
```

`make verify` выполняет `ruff check`, `ruff format --check`, `pytest` и `git diff --check`.
Для автоматического форматирования — `make format`, затем снова `make verify`.
Для просмотра всей функции: `git diff main...HEAD`.

## Запрещённые действия

- Коммитить `.env`, токены, пароли, БД, логи, `.venv` и кэши.
- Удалять тесты, отключать анализаторы, ослаблять критерии или будущий CI ради зелёного результата.
- Подменять проверку непроверенным заявлением или чужим авторством коммита/review.
- Публиковать непроверенные изменения прямо в `main`, обходить задачу и PR.
- Делать force push общей ветки, переписывать общую историю или перемещать выпущенные теги.
- Разрешать конфликт слепым выбором одной стороны без чтения обеих версий.

## Приёмка

Рецензент проверяет соответствие задаче и ТЗ, понятность решения, тесты,
контракт API, целостность данных и отсутствие секретов. Проверки должны пройти
на итоговой версии diff, а не только до последних изменений.
Критические файлы приёмки: `Makefile`, `pyproject.toml`, `tests/`,
`requirements*.txt`, `.gitignore`, `CONTRIBUTING.md`. Их изменения в PR
нужно отметить отдельно и проверить; их нельзя ослаблять без обоснования.

При неуспешной проверке изменение не принимается. Автор исправляет причину,
повторяет проверки и запрашивает повторный review. Самопроверка автора не
заменяет review другого участника и живую защиту преподавателю.

## Секреты и локальные файлы

```bash
git check-ignore -v .env .env.local instance/campus.sqlite3 .venv/bin/python
git ls-files -- .env '.env.*' '*.sqlite*' '*.db' '.venv/*'
```

Первая команда должна показать правила исключения, вторая — только безопасный
`.env.example`. `.gitignore` не защищает уже отслеживаемые файлы:
всегда проверяйте `git diff --cached` перед коммитом. Если секрет случайно
опубликован, его нужно отозвать; удаления строки следующим коммитом недостаточно.

CI, контейнеры и развёртывание не добавляются в рамках ЛР1.
