# Развёртывание на двух Linux-серверах

Развёртывание рассчитано на две чистые Ubuntu Server 24.04 без контейнеров.
Конфигурация стенда:

| Узел | Имя | Постоянный адрес | Открытые входящие порты |
|---|---|---:|---|
| приложение | `campus-app` | `172.16.114.10/24` | 22 из сети администрирования, 8000 из клиентской сети |
| база данных | `campus-db` | `172.16.114.20/24` | 22 из сети администрирования, 5432 только от `172.16.114.10` |

Обе VM подключены к общей NAT-сети VMware Fusion `172.16.114.0/24` со шлюзом
`172.16.114.2`. Статические адреса выбраны вне DHCP-пула `.128-.254`. Лишний
второй адаптер `ens256` на сервере БД отключён в Netplan, чтобы не было двух
маршрутов по умолчанию.

## 1 Создание машин и постоянные адреса

Для каждой VM требуется минимум 1 CPU, 1 ГиБ RAM и 10 ГиБ диска.
Имена узлов задаются командами:

```bash
sudo hostnamectl set-hostname campus-app  # первая VM
sudo hostnamectl set-hostname campus-db   # вторая VM
```

Имена интерфейсов определяются через `ip -br link` и указываются в соответствующем
шаблоне из `deploy/netplan`. Конфигурация копируется в `/etc/netplan/01-campus.yaml`
с правами `0600` и применяется командами:

```bash
sudo netplan try
sudo netplan apply
ip -br address
ping -c 2 172.16.114.20  # с campus-app
ping -c 2 172.16.114.10  # с campus-db
```

`netplan try` автоматически откатит ошибочную сетевую конфигурацию, если её не
подтвердить. Консоль VM остаётся открытой до проверки SSH.

## 2 SSH и пользователи

Ключ создаётся на компьютере администратора при первоначальной настройке:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/campus_lab
```

На обе VM передаются репозиторий и открытый файл `campus_lab.pub`.
Приватный ключ остаётся на компьютере администратора. На каждой машине:

```bash
cd /путь/к/Project_DevOps
sudo deploy/scripts/bootstrap-common.sh /путь/к/campus_lab.pub
```

После настройки проверяется новая SSH-сессия
`ssh -i ~/.ssh/campus_lab devopsadmin@172.16.114.10` (затем `.20`) и лишь
потом закрывается старая.
Скрипт создаёт `devopsadmin`, устанавливает для него ключевой доступ и
`NOPASSWD`-sudo, затем запрещает root/password login. Пароль этому пользователю
не задаётся: административный доступ определяется наличием приватного SSH-ключа.
Пользователь службы `campusapp` создаётся следующим скриптом без интерактивного
shell.

## 3 Сервер PostgreSQL

На `campus-db`:

```bash
cd /путь/к/Project_DevOps
sudo deploy/scripts/setup-db-server.sh 172.16.114.10 172.16.114.20 172.16.114.0/24
```

Пароль задаётся интерактивно, длина — не менее 16 символов. Разрешены буквы,
цифры, `_` и `-`; это исключает неоднозначный разбор `EnvironmentFile`. Скрипт устанавливает
PostgreSQL, создаст БД, роли, таблицы, `pg_hba.conf` и UFW. `campus_owner` не может
войти в систему и владеет объектами; `campus_app` может подключаться и выполнять
только CRUD над данными и использовать последовательности.

## 4 Сервер приложения

На `campus-app` с той же версией репозитория:

```bash
cd /путь/к/Project_DevOps
sudo deploy/scripts/setup-app-server.sh 172.16.114.20 172.16.114.0/24 172.16.114.0/24
```

Используется тот же пароль БД. Скрипт устанавливает Python/Gunicorn, копирует приложение в
`/opt/campus/app`, создаёт закрытый `/etc/campus/campus.env`, устанавливает и запускает
`campus.service`, затем настроит UFW. Исходники доступны на чтение группе службы,
но изменяются только root; пароль доступен root и группе `campusapp`.

Интерфейс доступен по `http://172.16.114.10:8000`.
Прямое открытие шаблона `campus/templates/index.html` через `file://` не запускает
Flask и не обеспечивает загрузку стилей, JavaScript и API.
Повторное развёртывание выполняется той же командой; после обновления кода
служба перезапускается:

```bash
sudo systemctl restart campus
```

## 5 Проверка

```bash
# campus-app
sudo /opt/campus/app/deploy/scripts/verify-host.sh app

# campus-db, из рабочего клона
sudo deploy/scripts/verify-host.sh db
```

Проверки перезагрузки, отказа БД, процессов, портов, журналов, параметров службы
и сетевой изоляции описаны в [регламенте эксплуатации](../docs/OPERATIONS.md).

## Ограничения безопасности

- `/etc/campus/campus.env`, приватные SSH-ключи и дампы БД не входят в Git;
- штатное управление Gunicorn выполняется через `systemctl`, без ручного запуска от root;
- порт 5432 разрешён только для сервера приложения, общего правила UFW нет;
- перед отключением парольного SSH проверяется вход по ключу;
- скрипты рассчитаны на свежие учебные VM: существующие посторонние правила UFW
  они не удаляют, их отсутствие нужно проверить вручную..
